# 研究路线图

本文档回答老师提出的三个问题，并把"系统优化"与"安全"两个阶段拆成可以逐条落地的任务，
每条任务都标注了对应的代码位置。

---

## 0. 当前进度

已完成（本仓库）：

- 可运行的 **baseline prototype**：车辆跨 cell 移动 -> handover -> 服务在边缘节点间迁移。
- 四种迁移策略：`reactive`（基线）、`reactive_delta`、`proactive`、`proactive_delta`。
- 真实数据：San Francisco cabspotting、Rome taxi、DATA7（Pisa，30 个真实 gNB +
  SUMO 轨迹）；三条链路都跑通。
- 指标分三批：
  1. 连续性、迁移成本、**可观测侧信道**；
  2. 每服务中断、提前量、切换前就绪、到达后滞后、迁移/停留比、冗余率；
  3. 带宽-时间积、并发迁移、控制面流数量、排队时间占比。
- 增量迁移按 **`(服务, 节点)` 记 base**：冷目标回退全量，恢复开销计入。
- 预测器：oracle（上限）、一阶马尔可夫（留一车训练）、last-direction，并统计
  next-cell 准确率。
- base 维护（向相邻节点复制）已实现，但暂搁置：能降中断，总流量却接近翻倍。
- "策略 x 车速"扫描 + 出图 + 自检脚本。
- 拓扑/移动/服务三个维度都可替换：规则网格或真实基站站点，合成轨迹或 Rome/SF 出租车轨迹，
  四类 MEC 服务的参数集中在 `services/catalog.py`。

已验证的核心现象：

- 中断比例随车速显著恶化：baseline 从 9.7%（15 km/h）升到 56.2%（90 km/h）。
- 增量收益取决于 base 命中：SF 冷目标 41.7% -> 字节省 47%；Rome 54.6% -> 省 28%；
  合成 92.9% -> 只省 2.4%。
- pre-copy 把中断压到个位数百分比，但字节成本不变 —— 形成明确的 Pareto 前沿。
- 真实出租车主要花在传状态；合成路线主要花在拉镜像（约 75% 的迁移时间）。
- 压力矩阵（80 组）：100 Mbps/12 车 reactive 从 65.7%（20 km/h）升到 92.3%（90）；
  500 Mbps 从 17.0% 到 72.3%；1 Gbps 从 8.7% 到 39.2%。
- proactive 中断只有 0–2%，但 P95 迁移/停留比在 constrained 60、high_load 90、
  worst 40 超过 1：**服务可用，但状态追不上车**。
- 真实预测器远不如 oracle：DATA7 上 next-cell 准确率 oracle 100%、Markov 49.2%、
  last-direction 21.2%；差预测会让迁移数据从 140 GB 涨到 214 GB（比 reactive 还多）。

## 1. 系统优化：三个方向

### 1.0 定位：follow-me、学习型策略，以及本文把赌注压在哪里

**follow-me 就是本仓库的 `reactive`。** 文献里最早、也最常被当作对照的迁移策略是
"用户走到哪个节点，就把状态跟到哪个节点"（follow-me / always-migrate）：切换之后立刻把
全量状态搬到新节点。`migration/strategies.py` 里的 `reactive` 正是这个策略，
`reactive_delta` 是它的"只搬增量"变体。**baseline 的命名在论文里要统一成 follow-me**，
否则审稿人会以为对照是自己发明的。

**关于深度/强化学习策略。** 近几年确实有大量工作用 DRL（DQN / PPO / SAC 等）来决定
"何时迁、迁到哪、迁谁"，并且在各自实验里优于 follow-me 一类的启发式。但把它当作本课题
主线，我认为不划算，理由按重要性排四条：

1. **差异化的地方不在策略层。** 策略层已经非常拥挤，而且结论对仿真参数高度敏感
   （链路带宽、状态大小、并发负载）。相比之下，"一次迁移到底要搬多少字节、花多长时间"
   是更底层、更难被参数淹没的贡献点。
2. **真正的瓶颈是仿真吞吐，不是 GPU。** 单次 `configs/default.yaml`（1800 步、12 辆车）
   在本机约 9 秒；DRL 一般需要 10^4 ~ 10^5 个 episode，即使只做离线训练也是几十到几百
   小时。EdgeSimPy 是单核 Python，没有 GPU 可加速——**没有 GPU 只是次要原因**，
   主因是每次采样的仿真代价。
3. **策略层的收益会被传输层吃掉，而这句话本身就是结论。** 迁移越便宜，换一个更聪明的
   "何时迁"决策带来的收益就越小。先做传输层优化再回头看 policy 的边际收益，会得到一条
   可量化的"收益递减"曲线——比再刷一个 DRL 的 SOTA 有意思，也更容易讲清楚。
4. **对照口径的风险。** 只和弱的 follow-me 比会被质疑"baseline 太弱"。稳妥做法是把 DRL
   放进 related work，实验里保留两个诚实的对照：**follow-me**（本仓库 `reactive`）与
   **完全不迁移**（远程访问，见 1.3 第 4 条）。

**第 3 条已经有数据支持**，不用等新实验。用现有的 `results/sweep/sweep_summary.csv`
直接算"把 follow-me 换成 proactive 能少多少中断"（单位：百分点，
`= 中断(follow-me) − 中断(proactive)`，正数表示换策略有收益）：

| 车速 (km/h) | 策略增益 · 全量状态 | 策略增益 · 增量状态 |
|---|---|---|
| 15 | **+8.21** | +0.32 |
| 30 | **+15.63** | +0.21 |
| 45 | **+26.03** | 0.00 |
| 60 | **+29.98** | −1.45 |
| 90 | **+49.00** | −3.11 |

全量状态下，换一个更聪明的时机策略收益高达 49 个百分点；**一旦把状态传输换成增量，
收益直接塌到 0 附近，高速下甚至变负**（预迁移被路线变化带偏）。

> 建议把这张表做成论文的一张图（x = 车速，y = 策略增益，两条线：全量 vs 增量）。
> 它比任何文字都更能说明"为什么本文把力气花在传输层"。
> **caveat**：这是单一拓扑 + 合成轨迹 + 理想前视（oracle look-ahead）的结果，
> 需要 M2 用真实数据集复核；高速段的负值也要确认不是偶然。

**如果将来想要一点"学习"的味道又没有 GPU**：这个决策空间只有三四个维度（车速、节点负载、
状态大小），用**上下文赌博机 / 表格 Q-learning / 线性函数近似**就足够，CPU 完全跑得动。
但那仍属于策略层贡献，建议只作为补充实验，不占主线。

> 一句话总结本课题的取舍：**不学策略，改传输。** 策略层用 follow-me 兜底，
> 把"搬什么 / 什么时候搬 / 怎么搬得快"这三件事做到极致。

### 1.1 迁移策略（何时迁、迁到哪里、迁谁）—— 次要方向

**现状**

- 时机：`reactive` = follow-me（切换之后再迁）vs `proactive`（接近 cell 边界时预迁移）。
- 预测器：`oracle`（真实未来，仅上限）、`markov`（一阶转移，留一车训练）、
  `last_direction`（方向外推）；DATA7 上 next-cell 准确率分别为 100%、49.2%、21.2%。
- 目标节点：固定为"当前/下一 cell 的边缘服务器"（`_target_coordinates` + `_server_at`）。
- 对象：一辆车的四个服务全部迁移。

### 1.2 迁移底层优化（怎么把一次迁移做快、做便宜）—— **主攻方向**

传输层可以拆成三个**可以独立做 A/B、可以独立归因**的层次。每一层都对应不同的指标，
也都有现成的代码钩子，因此论文里能分别回答"这一层的收益是多少"：

| 层次 | 手段 | 直接影响的指标 | 代码钩子 |
|---|---|---|---|
| **搬什么** | 增量粒度、压缩、去重、公共状态共享 | `state_mb_total`、`overhead_ratio` | `controller._start_migration()` 里设置 `service.state` |
| **什么时候搬** | 镜像预热/预取、预迁移时机、批量合并 | `p95_migration_duration_steps`、`mean_layer_pull_steps` | `_target_coordinates()`；主动往 `EdgeServer.waiting_queue` 推层 |
| **怎么搬得快** | 流优先级与带宽切片、并发度、多路径/中继 | `mean_state_transfer_steps`、`mean_link_utilisation` | `Simulator(network_flow_scheduling_algorithm=...)`、`max_concurrent_layer_downloads` |

**现状**

- 镜像按层缓存（EdgeSimPy container registry），只有未缓存层会传输。
- 状态支持"全量 / 增量"两种传输量。

## 2. 安全阶段：从侧信道到轨迹推断

> ⚠️ 动手之前先读 [`docs/related_work.md`](related_work.md) 第 4 节。
> "观测服务迁移可以定位用户"这个前提在 **JSAC 2017（chaff 论文）**里已经明确发表，
> 诱饵迁移的防御也在同一篇里做过。本阶段的可发表空间在于把问题从**单点定位**推进到
> **轨迹重构 + 速度维度**，并用**传输层优化节省的带宽**去补贴防御开销。

### 2.1 威胁模型

攻击者 = **外部被动观测者**（例如运营商之间的中间网络、被攻陷的交换机/链路监听点）。
它能观测到：

- 迁移**发生的时间**，
- 迁移的**源节点与目标节点**，
- （可能）迁移的**字节数**与持续时间。

它**不能**：解密迁移内容、看到车辆标识、看到应用层数据（这些都是防御的目标）。
攻击目标：由迁移序列推断车辆的移动轨迹 / 下一个 cell / 用户身份关联。

### 2.2 攻击者观测面（已经准备好）

每次运行都会输出 `observable_migration_trace.json`：

```json
[{"step": 132, "source_node": 7, "target_node": 13, "bytes": 210.4}, ...]
```

对照真值 `handovers.csv`（`step, vehicle_id, source_cell, target_cell`）。
迁移事件与握手事件天然一一对应，因此**baseline 相当于一个"明文广播轨迹"的系统**——
这正是要修的问题。

### 2.3 攻击实现与评估

1. **朴素攻击**：把迁移序列直接当作轨迹（当前 baseline 下准确率接近 100%），
   作为攻击上界。
2. **关联攻击**：用 (时间差, 节点对) 建图，做序列匹配/匈牙利算法，把事件聚类成"车辆"。
3. **推断攻击**：训练一个分类器（逻辑回归 / HMM / 序列模型），输入迁移事件序列，
   预测真实轨迹或下一个 cell。
4. **评估指标**：
   - 轨迹重构准确率 / 位置误差（Top-k cell 命中率），
   - 车辆身份关联准确率（正确聚类的比例，可用 F1），
   - 迁移可检测性（攻击者能否区分"有迁移"和"无迁移/伪装迁移"），
   - 推断所需的最少观测事件数。

### 2.4 防御族与实现钩子

| 防御 | 直觉 | 实现钩子 |
|---|---|---|
| 时序混淆 | 把迁移推迟到随机时刻，破坏"迁移时刻 ≈ 握手时刻"的耦合 | 控制器里给 `_start_migration` 加 `jitter`（以步为单位），配置项 `security.timing_jitter` |
| 诱饵迁移 | 在不移动的车辆上发起假迁移，稀释真实信号 | 控制器里周期性对随机 (服务, 目标) 调 `provision()`，用 `security.dummy_rate` 控制比例 |
| 路径填充 | 让迁移路径绕行/合并，隐藏"源-目标"真实相邻关系 | 迁移时把 `path` 换成非最短路径（`NetworkFlow` 的 `path` 参数），或经中继节点转发 |
| 批量/聚合 | 多个迁移同时发生，攻击者无法一一对应 | 与 1.1 的"批量迁移"共用实现，加 `security.batching` |
| 状态无关填充 | 迁移字节数固定/加噪，隐藏状态大小这一辅助特征 | `security.padding_mb`：在 `service.state` 上叠加随机填充 |
| 加密隧道 | 内容层保护（本工作聚焦元数据层，可作为对照实现） | 与路由/填充正交 |

**重要**：防御会引入额外开销（更多字节、更长迁移、更多中断），因此安全阶段的评估必须复用
第一阶段的三类指标，报告"**安全性 - 连续性 - 成本**"三维权衡。

### 2.5 安全指标

- 轨迹推断准确率 / 位置误差（攻击者视角，越低越好）
- 迁移事件的可区分度（AUC / KL 散度，接近随机最好）
- 防御开销：额外字节、额外中断步数、额外时延（相对 baseline 的百分比）
- 安全 - 开销比：每降低 1% 推断准确率所付出的开销

### 2.6 代码落地方式

建议新增一层"安全包装"，不改动已验证的迁移逻辑：

```
myedgesimpy/security/
  threat.py        # 攻击者模型：从 observable_trace 生成观测
  attacks.py       # 朴素 / 关联 / 推断攻击
  defenses.py      # 时序抖动、诱饵、填充、批量（以策略装饰器形式挂在控制器外）
  evaluation.py    # 安全指标与图表
```

控制器已经具备两个接口点：

- `MigrationController._start_migration()`：插入抖动/填充/诱饵；
- `MetricsCollector.observable_trace()`：攻击者的输入，直接喂给 `attacks.py`。

## 3. 数据集与实验矩阵

| 维度 | 取值 |
|---|---|
| 移动数据集 | Rome、San Francisco（真实出租车轨迹）；合成轨迹作为对照 |

python -m myedgesimpy sweep --config configs/default.yaml \
    --speeds 15,30,45,60,90 \
    --strategies reactive,reactive_delta,proactive,proactive_delta \
    --out results/sweep

## 4. 论文叙事建议

1. **问题**：MEC 中车辆高速移动导致服务状态必须在边缘节点间频繁迁移；朴素迁移的
   中断与开销都不可接受（用本文 baseline 曲线量化）。
2. **贡献一（系统）**：一个可复现的、覆盖真实移动/网络/服务负载的迁移仿真框架，
   给出"车速 - 中断 - 开销"的基本规律（当前结果已可支撑）。
3. **贡献二（优化，主线）**：把迁移拆成"搬什么 / 什么时候搬 / 怎么搬得快"三层传输优化，
   逐层给出**收益归因**，并给出"中断 - 字节 - 时延"的 Pareto 前沿。当前结果已经能支撑
   第一版（增量状态 + pre-copy 把中断从 ~56% 压到 ~7%）；
   镜像预热、流优先级与带宽切片是接下来最自然的两个增量。
4. **贡献三（安全）**：迁移元数据本身是轨迹侧信道；给出攻击评估方法与防御族，
   报告安全-连续性-成本三维权衡（第二阶段）。
5. **定位说明（放在 related work，不是贡献）**：学习型迁移策略（DRL 等）现状与
   本文不采用的原因——策略层拥挤、仿真吞吐是真瓶颈、且传输层优化会压缩策略层收益。
   实验里以 follow-me 与"完全不迁移"两个对照兜住口径。
